## 4.3 Взвешенное среднее по трём целям

```
выполнение_цели = kpi_fact / kpi_plan * 100
взвешенный_процент = Σ(выполнение_цели × weight)
```

✅ **Веса: Ц1 = 0.40, Ц2 = 0.40, Ц3 = 0.20** (сумма = 1.0). Хранятся в одном месте — `config.GOAL_WEIGHTS`.

| Цель | Бизнес-цель | Вес |
|---|---|---|
| Ц1 Качество продукта | U1 | **0.40** |
| Ц2 Снижение Time to market | U2 | **0.40** |
| Ц3 Снижение зависимости от людей | U3 | **0.20** |

Пример: Ц1 = 120%, Ц2 = 90%, Ц3 = 105% →
`0.4×120 + 0.4×90 + 0.2×105 = 48 + 36 + 21 = 105.0%`

✅ **«КПИ выполнены» = взвешенное среднее ≥ 100%.**

⚠️ **Правка к v2.3.** В v2.3 веса были 1/3 на каждую, и там же утверждалось, что Ц3 участвует «наравне» с Ц1 и Ц2. Веса 40/40/20 этому противоречат: Ц3 весит вдвое меньше. Причина правки — приоритет отдан качеству и скорости, Ц3 остаётся значимой, но вспомогательной.

⚠️ Пример из v2.3 «120 / 90 / 75 → 95%» при новых весах даёт **97.5%**, а не 95%. Приведённый выше пример заменяет его.

⚠️ Для периодов, где Ц3 ещё не ставилась, веса Ц1/Ц2 = 50/50 (`config.GOAL_WEIGHTS_TWO`).

## 4.4 Шкала A–E и статусы внедрения

### 4.4.1 Статусы внедрения

Каждая цель имеет поле `deploy`. Допустимые значения — только из `config.DEPLOY_STATUSES`, порядок возрастания:

| Статус | Смысл |
|---|---|
| `none` | не внедрено |
| `deployed` | внедрено |
| `in_use` | внедрено **и работает** |

⚠️ **Единственное правильное имя статуса — `deployed`.** Синоним `done` недопустим: он приводил к падению `overall_deploy` (`ValueError`). В `overall_deploy` добавлена защита: неизвестный статус пропускается, расчёт продолжается.

⚠️ **Статус внедрения сотрудника (`overall_deploy`) — лучший из статусов активных целей.** Достаточно одной цели в `in_use`, чтобы сотрудник считался «внедрено и работает». Обоснование: цели равноправны, а работающий в проде результат по любому направлению — факт, а не намерение.

### 4.4.2 Буква A–E

Считается по взвешенному проценту (§4.3) и статусу внедрения:

| Условие | Буква | Подпись |
|---|---|---|
| `percent < 50.0` | **E** | Провал (КПИ < 50%) |
| `50.0 ≤ percent < 70.0` | **D** | Плохо (50–70% КПИ) |
| `70.0 ≤ percent < 100.0` | **C** | Удовлетворительно, **КПИ не выполнены** (70–100%) |
| `percent ≥ 100` и `deploy = in_use` | **A** | Отлично: КПИ выполнены, внедрено и используется |
| `percent ≥ 100` и `deploy ≠ in_use` | **B** | Хорошо: КПИ выполнены, внедрено |

Пороги хранятся в `config`:

```python
LETTER_E_MAX = 50.0
LETTER_D_MAX = 70.0
LETTER_C_MAX = 100.0
```

⚠️ **Правка к v2.3.** Подпись C «КПИ выполнены» **неверна**: C выдаётся при 70–100%, где КПИ как раз не выполнены. Правильная подпись — «Удовлетворительно, КПИ не выполнены (70–100%)». `config.MARK_LABEL["C"]` исправлен.

⚠️ **Полоса B — это ровно `percent ≥ 100` при `deploy ≠ in_use`.** Так как `LETTER_C_MAX = 100`, ширина B ниже 100% равна нулю. При текущих данных B не получает никто.

⚠️ **«Второй D подряд → E» в этой версии не реализуется.** Код не хранит историю букв за прошлые периоды. Из подписи E этот случай исключён до появления истории.

### 4.4.3 Запрет на надбавку без грейда

⚠️ Если `grade_source = "default"` (оценок компетенций не было никогда, грейд взят фолбэком `GRADES[0]`), то:
- `bonus_pct = None`
- `bonus = 0`

Причина: до правки сотрудник без единой оценки получал 12% надбавки как за нормальный грейд. Спасал только нулевой оклад.

## 4.5 Премия

### 4.5.1 Формула

```
премия, ₽ = оклад × BONUS_BASE_RATE × (1 + grade_share) × MARK_K[буква]
премия, % = BONUS_BASE_RATE × (1 + grade_share) × MARK_K[буква] × 100
BONUS_BASE_RATE = 0.20
```

| Буква | `MARK_K` | Премия при `grade_share = 0` | При `grade_share = 0.3` |
|---|---|---|---|
| A | 1.2 | 24% | 31.2% |
| B | 1.0 | 20% | 26% |
| C | 0.6 | 12% | 15.6% |
| D | 0.3 | 6% | 7.8% |
| E | 0.0 | 0% | 0% |

### 4.5.2 Что такое `grade_share`

⚠️ **`grade_share` — это НАДБАВКА ЗА ГРЕЙД, а не доля внутри коридора.** Значение берётся из третьего поля `config.GRADES` и зависит **только** от грейда.

```python
def grade_for(percent):
    """Грейд по среднему баллу компетенций -> (название, доля премии)."""
    name, share = config.GRADES[0][0], config.GRADES[0][2]
    for g in config.GRADES:
        if percent >= g[1]:
            name, share = g[0], g[2]
    return name, share
```

**Грейд определяется средним баллом компетенций** (в процентах от `MAX_SCORE`), а не KPI:

| Средний балл компетенций, % | Грейд | `grade_share` |
|---|---|---|
| < 65 | Джун 1 | **0.0** |
| ≥ 65 | Джун 2 | **0.1** |
| ≥ 75 | Мидл 3 | **0.15** |
| ≥ 82 | Мидл 4 | **0.2** |
| ≥ 90 | Сеньор 5 | **0.25** |
| ≥ 96 | Сеньор 6 | **0.3** |

⚠️ **Это ступени, а не прогресс.** Все сотрудники ниже 65% балла получают одинаковые `0.0`. Разница `0.0 / 0.1 / 0.15` между людьми означает **разные грейды**, а не разную позицию внутри одного грейда.

⚠️ **Правка к ред. 1 §4.5.2.** Раньше здесь было написано «доля внутри коридора от 0.0 до 1.0» и «у трёх человек с „(1/3)“ share может быть 0.0, 0.1 и 0.15». Это неверно: `grade_for` возвращает фиксированное поле грейда, внутри грейда `share` не меняется.

⚠️ **«(1/3)» и `grade_share` — разные величины.** «1/3» в интерфейсе — число пройденных критериев перехода на следующий грейд (`next_grade_gap`). `grade_share` — надбавка текущего грейда. Путать нельзя.

### 4.5.3 Известный дисбаланс (принят осознанно)

⚠️ Формула смешивает две независимые системы: **буква** приходит из KPI (цели), **`grade_share`** — из компетенций (грейд). Следствия:

| Случай | Премия |
|---|---|
| A, `grade_share = 0` | 24% |
| C, `grade_share = 0.3` | **15.6%** |

⚠️ Разрыв сокращён: при новых ступенях A на младшем грейде (24%) обгоняет C на старшем (15.6%) в 1.54 раза — это **нижняя граница**. На фактических данных разрыв шире: Волков A (26.4%) / Сидоров C (13.8%) = **1.91×**; максимум при `share = 0` у C — 26.4 / 12 = **2.2×**. Раньше при `share` до 1.0 C могла догнать A. Цель — **KPI остаётся решающим фактором**. Цена: сотрудник с высокими компетенциями и слабым KPI теряет много, даже будучи формально «старше».

### 4.5.4 Нет грейда — нет премии

⚠️ При `grade_source = "default"` надбавка равна нулю, независимо от буквы (см. §4.4.3).

⚠️ Внутри `evaluate` при `source = "default"` значение `grade_share` остаётся **`0.0`** (это корректная надбавка Джун 1, а не признак отсутствия данных). Обнуление премии обеспечивается отдельным условием, а не подменой `share` на `None`.

⚠️ **`grade_source` принимает три значения:** `scores` (оценки компетенций за расчётный период), `period` (оценки за другой период — грейд из последней непустой анкеты), `default` (оценок не было никогда). Надбавка и премия начисляются при `scores` и `period`; при `default` обнуляются. Значение `period` появилось в коде раньше, чем было описано здесь — правка 30.10.2026.

### 4.5.5 Блокировка премии по заполненности анкеты

⚠️ Премия блокируется, если приоритетные компетенции заполнены **≤ 90%**. При 95% блокировки нет.

| Заполненность анкеты | Премия при A и окладе 150 000 ₽ |
|---|---|
| 100% | 36 000 ₽ |
| 95% | 31 200 ₽ |
| 90% | **0 ₽** |

⚠️ Блокировка действует **независимо от буквы и грейда**: буква A при анкете 90% даёт 0 ₽.

⚠️ **Мотив.** Неполная анкета искажает средний балл компетенций, а значит грейд и `grade_share`. Без блокировки сотрудник с одной оценкой «5» получал бы надбавку выше, чем полностью оценённый. Блокировка — грубый, но однозначный способ закрыть этот обход.

⚠️ Порог «≤ 90%» выбран под фактические данные: у 12 из 13 сотрудников анкета заполнена на 90–95%. Подробности — вопросы 27 и 28 в §13.3.

## 4.6 Разделение страниц

⚠️ В v2.3 назначение страниц не описано. Фиксируется:

| Страница | Что показывает | Чего не показывает |
|---|---|---|
| `/team` | Оклад, грейд, средний балл, **букву A–E**, **КПИ, %**, **премию в рублях**, **«Анкета»**, до следующего грейда | Детализацию Ц1/Ц2/Ц3, состав компетенций |
| `/scores` | Период, число сотрудников, число «КПИ выполнены», сводку букв, по каждому: оклад, Ц1–Ц3, взвеш. %, букву | Грейд, компетенции, премию в рублях |
| `/matrix` | Оценки компетенций по сотруднику за период | KPI и премию |

⚠️ **Колонка «Анкета» (правка 30.10.2026).** В `/team` рядом с буквой, КПИ и премией показывается процент заполненности приоритетных компетенций. Значение участвует в блокировке премии (§4.5.5), поэтому должно быть видно там же, где премия.

⚠️ **Формат колонки «до следующего грейда» (правка 29.10.2026).** Колонка показывает
счётчик `п1 >= 4: X/Y`, где `Y` — число **оценённых** приоритетных компетенций,
`X` — сколько из них не ниже 4. При отсутствии оценок — «оценок нет».
Неполнота анкеты показывается отдельной строкой «не оценено N».
Знаменатель — число оценённых, а не общее число приоритетных: иначе пустой профиль
давал ложное `20/20` (Якин), а условие «оценено всё» гасило счётчик у 12 из 13.

⚠️ **Пометка «Оценка A–E по целям — Этап 2» с `/team` снята**: буква на странице есть. Вместо неё — пояснение формулы: «Буква и КПИ считаются по целям с весами 40/40/20, премия — оклад × 20% × (1 + надбавка грейда) × коэффициент буквы».

⚠️ **Навигация.** Все страницы выведены в верхнее меню (`TABS` в `app.py`), порядок: «Дашборд» → «Команда» → **«Результаты»** → «Оценки» → «Компетенции» → «Цели» → «Проекты». До правки `/scores` в `TABS` не было: страница работала, но попасть на неё можно было только по прямой ссылке. «Результаты» стоят соседней вкладкой с «Командой», потому что обе показывают срез по людям за период.

⚠️ **Источник истины для расчёта — единственный: `grading.evaluate(employee, goals)`.** Любая страница берёт `kpi_percent`, `deploy`, `letter`, `bonus_pct`, `bonus` оттуда.

✅ **Ловушка модулей закрыта (28.10.2026).** В `app.py` стояло `import grading_compat as grading` — имя `grading` перекрывалось слоем совместимости, где **нет** `evaluate`, отсюда `AttributeError: grading_compat has no attribute 'evaluate'`.

⚠️ Теперь импорты разведены явно:

```python
import grading                    # расчёт: grading.evaluate(employee, goals)
import grading_compat as compat   # цели: compat._goals_for(emp)
```

⚠️ Псевдоним `grading_core` больше не используется — он был обходом, а не решением. Правило: **слой совместимости не должен называться `grading`**.
