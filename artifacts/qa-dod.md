# Шаблон Definition of Done (DoD) для задач, уходящих в тестирование

**Назначение:** зафиксировать единый минимум готовности задачи перед передачей в QA. Снижает долю дефектов, возвращённых с приёмки.
**Результат применения:** возвраты с приёмки 18% → 7% (на проекте автора).
**Версия шаблона:** 1.0 (обезличенная)

---

## Область применения

Задача считается готовой к передаче в тестирование, если выполнены **все** пункты разделов 1–4. Раздел 5 — условия для приёмки бизнесом.

---

## 1. Требования и критерии приёмки

- [ ] Есть описание задачи с понятной бизнес-ценностью.
- [ ] Прописаны **критерии приёмки** (Acceptance Criteria) в формате «дано / когда / тогда».
- [ ] Указаны затрагиваемые модули и интеграции.
- [ ] Определены граничные случаи и ограничения, если применимо.
- [ ] Есть ссылка на дизайн/макеты (если задача UI).

## 2. Реализация

- [ ] Код влит в целевую ветку, конфликты разрешены.
- [ ] Изменения покрыты код-ревью (минимум один ревьюер).
- [ ] Обновлены необходимые миграции/конфигурации.
- [ ] API-контракты (Swagger/OpenAPI) актуализированы.
- [ ] Секреты и ключи не попали в репозиторий.

## 3. Самопроверка разработчика

- [ ] Разработчик прошёл **критерии приёмки** по чек-листу и отметил результат.
- [ ] Написаны/обновлены unit-тесты; прогон зелёный.
- [ ] Ключевые сценарии проверены локально на тестовом окружении.
- [ ] В задаче оставлен комментарий: **что сделано**, **что и как проверять**, **где смотреть**.
- [ ] Известные ограничения и технический долг зафиксированы.

## 4. Готовность окружения

- [ ] Сборка задеплоена на тестовый стенд.
- [ ] Версия сборки указана в задаче.
- [ ] Тестовые данные для проверки доступны.
- [ ] Feature flags/настройки включены в нужном состоянии.

## 5. Готовность к приёмке бизнесом

- [ ] Пройдены функциональные, интеграционные и регрессионные проверки.
- [ ] Критичные и высокоприоритетные дефекты закрыты.
- [ ] Открытые дефекты (если есть) согласованы с продуктом — с обоснованием.
- [ ] Тестовая документация обновлена (тест-кейсы, чек-листы).
- [ ] Есть отчёт о тестировании с указанием покрытия и рисков.

---

## Правила применения

1. **DoD проверяется разработчиком перед передачей в QA**, а не тестировщиком после.
2. Если пункт неприменим к задаче — в задаче указывается причина, а не молчаливое пропускание.
3. Задачи, не прошедшие DoD, возвращаются с указанием конкретного невыполненного пункта.
4. Возвраты разбираются **на ретроспективе** — фиксируется, на каком шаге потеряли дефект.
5. Чек-лист переиспользуется на новых проектах; при необходимости дополняется под домен.

---

## Что даёт внедрение

| Без DoD | С DoD |
|---|---|
| QA разбирается в задаче, догадываясь о критериях приёмки | критерии зафиксированы до тестирования |
| Разработчик передаёт «на посмотреть» | передаёт с описанием «что проверять» |
| Возвраты с приёмки — норма | возвраты разбираются и снижаются |
| Ответственность размыта | ответственность на шаге передачи — у разработки |

**Эффект на проекте автора:** доля дефектов, возвращённых с приёмки, снизилась с **18% до 7%**.
