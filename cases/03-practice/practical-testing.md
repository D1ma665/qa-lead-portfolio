# Кейс 5. Практическое тестирование: чек-лист и дефекты

> **Формат:** проблема → действия → результат
> **Роль:** QA Lead (остаюсь практиком — тестирую лично)
> **Продукт:** мобильное приложение (iOS), версия 2.0.8.5 · iPhone 5s, iOS 12.4.7
> **Артефакты:** [чек-лист авторизации/регистрации](../artifacts/checklist-auth-mobile.md) · [образец баг-репортов](../artifacts/bug-reports-sample.md)

---

## 🔴 Проблема

Авторизация и регистрация в мобильном приложении тестировались **фрагментарно**: отдельными «кусками» функционала, вне пользовательского пути. В результате:

- Дефекты находились **пользователями**, а не командой.
- Баг-репорты оформлялись по-разному — разработчикам приходилось выяснять детали в переписке.
- Негативные и граничные сценарии оставались вне покрытия — а именно там живут дефекты валидации и безопасности.
- Проверялось «кнопка нажимается», но не **куда она ведёт** и что происходит **между экранами**.
- Состояния приложения (чистая установка против повторного запуска) не учитывались.

**Задача:** поднять качество тестирования авторизации/регистрации, не увеличивая команду.

---

## 🟡 Действия

### 1. Построил чек-лист вокруг пользовательских путей

Проверки сгруппированы по функциональным блокам, внутри блока — порядок, соответствующий пути пользователя:

| # | Блок | Что проверяется |
|---|---|---|
| 0 | Первая установка | лицензионное соглашение, кнопка «Get started» → HOST |
| 1 | Регистрация «Create account» | существующий/несуществующий email, пустые поля |
| 2 | Авторизация «Log in» | валидные/невалидные данные, пустой пароль |
| 3 | Показать / скрыть пароль | переключение видимости, состояние иконки |
| 4 | Авторизация через Facebook | успех, отказ, запрет email, отказ после успеха |
| 5 | Состояния списка сохранённых аккаунтов | чистая установка vs повторный запуск |
| 6 | Кнопки «Create»/«Login» на экране аккаунтов | корректность перехода |
| 7 | Вход в последний аккаунт | вход без пароля |
| 8 | Скрытие модального окна | состояние приложения не теряется |
| 9 | Восстановление пароля «Forgot password» | успех, несуществующий аккаунт |
| 10 | Клавиатура и адаптивность | автозакрытие, перекрытие текста |
| 11 | Экран последних аккаунтов | отображение, смена, удаление, заглушка |
| 12 | «Rate US» | переход в AppStore, форма отзыва |
| 13 | «Report a problem» | открытие раздела, отправка формы |
| 14 | Подписка на push | запрет уведомлений → popup в настройки |
| 15 | Редактирование профиля | аватар, имя, email |

**Итого:** 15 разделов, **40+ проверок**, каждая помечена типом:

- ✅ **happy path** — основной сценарий
- ❌ **негативный** — некорректный ввод, отказ
- ⚠️ **граничный** — лимиты, пустые поля, спецсимволы

### 2. Принципы, по которым строился чек-лист

1. **Покрытие пользовательских путей целиком** — от установки до редактирования профиля, а не отдельные «куски».
2. **Явное разделение happy path / негативных / граничных** — при регрессе быстро выбирается нужный набор.
3. **Проверка связок между экранами** — не только «кнопка нажимается», но и куда она ведёт (п. 0.2, 6, 12).
4. **Учёт состояний приложения** — чистая установка против повторного запуска (п. 5).
5. **Валидация ввода как отдельная ось** — пустые поля, неверные данные, спецсимволы (п. 1.3–1.4, 2.2–2.5).

### 3. Ввёл единый стандарт баг-репорта

Каждый дефект описывается по шаблону: заголовок → окружение → предусловия → шаги воспроизведения → ожидаемый результат → фактический результат → severity / приоритет / влияние.

## 🟢 Результат

### Найдено и оформлено 5 дефектов

| # | Дефект | Область |
|---|---|---|
| Bug_1 | Регистрация на несуществующий email проходит без предупреждения | логика валидации |
| Bug_2 | Неверное сообщение об ошибке при невалидном пароле | тексты / UX |
| Bug_3 | Возможна отправка пустого отчёта (только пробелы) | валидация ввода |
| Bug_4 | Доступен developer mode по двойному тапу по номеру версии | безопасность |
| Bug_5 | Поля Email/Password не фильтруют emoji и запрещённые символы | валидация / безопасность |

### Эффект

| Показатель | Значение |
|---|---|
| Покрытие пользовательских путей | целиком (установка → профиль) |
| Разделение проверок по типам | внедрено (happy/негатив/граница) |
| Единый стандарт баг-репорта | внедрён |
| Время выяснения деталей у автора дефекта | снижено (всё в репорте) |
| Найдены дефекты валидации и безопасности | 3 из 5 (Bug_3, Bug_4, Bug_5) |

**Главный вывод:** переход от фрагментарной проверки к покрытию пользовательских путей целиком вытащил дефекты, которые не находил ни один happy-path-сценарий. Чек-лист по путям + единый шаблон баг-репорта дали измеримый результат без расширения команды.

## 📌 Что забрал с собой

1. **Пользовательский путь важнее списка экранов** — проверки группируются вокруг задач пользователя.
2. **Разметка проверок** (happy/негатив/граница) не даёт забыть негативные сценарии.
3. **Связки между экранами** — проверять не только кнопку, но и куда она ведёт.
4. **Состояния приложения** — чистая установка и повторный запуск дают разные результаты.
5. **Единый шаблон репорта** экономит время всей команды и повышает доверие к QA.
