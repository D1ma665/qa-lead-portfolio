# Онбординг QA-команды: AI-first Testing

> Практическое руководство для нового QA-инженера.
> От «что это вообще» до «первый самостоятельный запуск».
> Прочитай целиком 1 раз, потом пользуйся как справочником.

---

## Часть 0. Зачем мы это делаем

**Как было раньше.** QA-инженер вручную проходил сайт, кликал по кнопкам,
искал баги, потом писал автотесты руками.

**Как теперь.** AI-агент сам обходит сайт заказчика, сам решает, что нажать,
находит баги и автоматически генерирует регресс-тесты.

**Твоя роль меняется.** Ты не «ручной кликер», а **наблюдатель и наставник агента**:
ревьюишь его находки и уточняешь логику под конкретный сайт.

### Главная ментальная модель

> **Ядро движка (`core/`) — универсальное. Всё под конкретный сайт — в YAML-профиле.**
> Наш продукт работает на **РАЗНЫХ** сайтах заказчиков.

Запомни это — из него следует всё остальное.

---

## Часть 1. Словарь

| Термин | Что значит простыми словами |
|---|---|
| Профиль | YAML-файл с настройками одного сайта (заказчика). Наш «пульт управления» |
| Ядро / core | Универсальная логика, не меняется под сайт |
| Адаптер | Правила «как вести себя» с типом сайта: `classic` или `spa` |
| Crawler | Собирает все кнопки/поля на странице |
| Brain | AI-мозг: решает, что кликнуть, и судит, баг ли это |
| Executor | Реально выполняет клики через Playwright |
| Oracle | Ловит сигналы багов (ошибки 500, JS-ошибки, пустая страница) |
| Reporter | Сохраняет баги в JSON + Markdown + скриншоты |
| Recorder | Превращает найденный баг в автотест |
| Engine | Оркестратор: гоняет обход по страницам |

## Часть 2. Первая установка (≈15 минут)

### Шаг 1. Клонируем и ставим зависимости

```bash
git clone <repo>
cd ai-first-qa
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
playwright install chromium      # скачает браузер для тестов
```

### Шаг 2. Настраиваем ключи

```bash
cp .env.example .env
```

Открываем `.env`, вписываем свой ключ OpenAI:

```
OPENAI_API_KEY=sk-...твой ключ...
```

> ⚠️ Файл `.env` никогда не коммитим — он уже в `.gitignore`.

### Шаг 3. Пробуем запустить на тестовом сайте

```bash
python main.py --profile profiles/example.yaml
```

Что должно произойти:

1. В консоли побегут строки `Страница: ...` и `→ click #5 (открыть меню)`.
2. Агент покликает сайт, поищет баги.
3. В конце появится: `Найдено багов: N`.
4. Создадутся папки `artifacts/<имя_профиля>/`.

Если видишь это — всё работает. 🎉

## Часть 3. Как это работает (схема в голове)

```
Профиль (YAML) ──► Engine (обход)
     │
     ├─► Crawler: собрал элементы
     ├─► Brain: "кликни #7" ──► Executor: кликнул
     ├─► Oracle: "тут 500-я ошибка" ──► Reporter: сохранил баг
     └─► ссылки ──► в очередь обхода
     │
Баг (JSON) ──► Recorder ──► pytest-тест (регресс)
```

Читай так: **профиль → движок гоняет сайт → баги → тесты.**

## Часть 4. Работа с сайтом заказчика (главная задача)

### 4.1. Создать профиль под нового заказчика

```bash
cp profiles/example.yaml profiles/<заказчик>.yaml
```

Открываем файл и правим только эти строки:

```yaml
name: client-ivanov              # имя (латиницей, без пробелов)
start_url: https://staging.ivanov.ru
allowed_domains:
  - ivanov.ru
locale: ru                       # язык сайта
adapter: classic                 # classic или spa
readonly: false                  # менять ли данные
```

> 💡 **Как понять classic или spa?**
> Открой сайт → правой кнопкой «Просмотр кода» → если body пустой,
> а контент грузится в `<div id="root">` или `<div id="app">` — это **spa**.
> Если текст сразу в HTML — **classic**.

### 4.2. Настроить защиту (важно!)

Всё, что нельзя нажимать, — в блок `safety`:

```yaml
safety:
  forbidden_keywords: [удалить, оплатить, деактивировать]
  forbidden_url_patterns: [logout, /delete, /checkout]
```

> 🔒 Даже если заказчик разрешил менять данные — опасные кнопки всегда
> в чёрном списке. Это наша подушка безопасности.

### 4.3. Запустить обход

```bash
python main.py --profile profiles/ivanov.yaml
```

### 4.4. Посмотреть результаты

```
artifacts/ivanov/
  bugs/SUMMARY.md          ← сводка: сколько багов и какие
  bugs/bug-001-*.md        ← читаемое описание бага
  bugs/bug-001-*.json      ← машинный формат
  screenshots/*.png        ← скрины-доказательства
```

## Часть 5. Ревью находок агента (ключевая работа!)

Агент — не истина в последней инстанции. Ты решаешь, настоящий баг
или ложное срабатывание.

Открываешь `bug-XXX.md` и проверяешь:

1. **Воспроизводится ли?** — руками повтори шаги из отчёта.
2. **Это баг или ожидаемое поведение?** — иногда AI путает.
3. **Severity верный?** — бот может завысить или занизить важность. Поправь priority.

Если баг ложный (паттерн повторяется) → сигнал доработать:

- добавить слово в `forbidden_keywords` профиля, если агент жмёт не то;
- уточнить промпт в `core/brain.py` (только с ревью тимлида).

## Часть 6. Генерация регресса

Когда баги отревьюены:

```bash
python run_regression.py --profile profiles/ivanov.yaml --regen
```

- `--regen` — заново сгенерирует тесты из найденных багов;
- тесты появятся в `artifacts/ivanov/generated_tests/`;
- команда тут же прогонит их через pytest.

> ⚠️ Сгенерированные тесты — **черновик**. Их нужно довести: уточнить ассерт,
> вынести селекторы, убрать лишние шаги. Считай их «каркасом» от бота.

## Часть 7. Правила безопасности (читаем дважды!)

1. 🔴 Только тестовые стенды. Никогда не гоняем на проде без `readonly: true`.
2. 🔴 Проверь `allowed_domains` — агент не должен уйти на чужой сайт.
3. 🔴 `forbidden_keywords` + `forbidden_url_patterns` заполнены под каждый сайт.
4. 🟡 Лимиты (`max_pages`, `max_depth`) — защита от бесконечного обхода
   и больших счетов за токены.
5. 🟡 Не коммить `.env` с ключами.
6. 🟢 Сомневаешься — спроси наставника до запуска.

## Часть 9. Что делать, если сломалось

| Симптом | Причина / что делать |
|---|---|
| `OPENAI_API_KEY` не задан | Нет `.env` или ключ пустой |
| Профиль не найден | Неверный путь в `--profile` |
| `executable doesn't exist` | Забыл `playwright install chromium` |
| Агент кликает не то | Дополни `safety` / уточни промпт (с тимлидом) |
| Обход ушёл в чужие домены | Проверь `allowed_domains` |
| Много ложных багов | Ревьюируй и корректируй — это нормально, учим движок под сайт |
| Счёт за токены растёт | Снизь `max_pages` / `max_actions_per_page` |

## Часть 10. Наставничество: как ведём новичка

Наставник ведёт коллегу по этапам:

1. **День 1** — вместе проходим установку (Часть 2) и первый запуск.
2. **День 2** — коллега сам создаёт профиль под тестовый сайт, ты проверяешь.
3. **День 3** — коллега самостоятельно гоняет и ревьюит баги, ты — на связи.
4. **Финал** — коллега проходит чеклист (Часть 8) без тебя.

**Принцип наставника:** не давать готовый YAML — а просить заполнить
и объяснить, почему `classic`, а не `spa`. Понимание важнее копипасты.
